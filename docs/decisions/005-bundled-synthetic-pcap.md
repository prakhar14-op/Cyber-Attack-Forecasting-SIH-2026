# 005 — Bundle the synthetic demo PCAP in git (deliberate exception) — **DECIDED**

**Status: decided 2026-09-07. `app/assets/synthetic_demo.pcap` stays committed.**

## The tension

CLAUDE.md ("Things not to do") says: *"Do not commit weights or `.pcap` files to git. Use
GitHub Releases and record the SHA-256."* BUILD_PLAN M11.4 simultaneously contemplates
bundling a demo capture so the app has an input on a bare machine. The submission audit
flagged the contradiction (minor severity) and asked for the exception to be recorded
explicitly rather than left implicit in `.gitignore`'s allow-list.

## Decision

Keep `app/assets/synthetic_demo.pcap` in git, as the **single** allowed `.pcap`, because:

1. **It is not capture data.** It is a deterministic, hand-authored, *synthetic* walk of the
   kill chain generated by `python -m capture.make_synthetic_demo` — no real traffic, no
   privacy surface, and it is never used for any reported metric (the app says so on screen).
2. **The offline demo must clone-and-run.** The PS's hard constraint is a fully offline demo;
   a Release-hosted asset would add a download step to the air-gapped flow the demo exists to
   prove.
3. **It is small and inert**: 4.65 MB (well under GitHub limits), regenerable byte-for-byte
   from the committed generator, and force-included via an explicit `.gitignore` negation
   (`!app/assets/synthetic_demo.pcap`) so every other `.pcap` remains blocked.

The general rule stands unchanged: **real captures and model weights never enter git** —
weights travel via GitHub Release with SHA-256s recorded in the README and enforced by the
engine's refuse-on-mismatch check (M9.3); any M11 lab capture ships the same way.

## Revisit if

- the synthetic file grows past ~10 MB, or
- a real M11 capture replaces it as the bundled demo input (then the bundled file must be the
  synthetic one or nothing — real captures go to a Release, per the rule above).
